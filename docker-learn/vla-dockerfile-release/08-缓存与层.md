# 08 缓存与层

> 另见：[brain-service 篇第 2 章 2.2–2.3](../brain-service-docker-deploy/02_context_and_cache.md)、[lab02](../brain-service-docker-deploy/code/lab02_cache/)

## 缓存规则

BuildKit 从上到下处理每条指令，判断能否复用上次的结果：

| 指令 | 判断依据 |
|---|---|
| `FROM` | 基础镜像是否变化 |
| `COPY` | 被拷贝文件的内容是否变化 |
| `RUN` | 命令字符串是否变化（**不管**命令实际下载了什么） |
| `ENV` `ARG` `LABEL` 等 | 指令内容和变量值是否变化 |

一旦某条指令没命中缓存，**它之后的所有指令都要重新执行**。

## 由此得出的写法原则

把变化少的放前面，变化多的放后面：

```dockerfile
# 好：改代码只会让最后一层失效
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY src/ ./src/

# 差：改一行代码，pip install 也要重跑
COPY . .
RUN pip install -r requirements.txt
```

## 两层镜像方案

原项目把这条原则推到镜像级别，拆成两个 Dockerfile：

| | Dockerfile.env | Dockerfile.release |
|---|---|---|
| 内容 | 系统库、torch、jax、相机 SDK 等第三方依赖 | 业务代码 |
| 构建耗时 | 长（大量下载和编译） | 短（拷文件加检查） |
| 重建时机 | 很少，`ENV_VERSION` 变化时 | 每次发版 |
| 产物 | `vla-body-env` `vla-brain-env` | `vla-body` `vla-brain` |

`Dockerfile.release` 的 `FROM` 直接引用 env 镜像，所以改代码只会重建 release 部分，几十 GB 的依赖层直接复用。推送到镜像仓库时，env 镜像的层已经在仓库里，只需要上传新增的代码层。

## 原文件里的缓存行为

- builder 阶段一开始就 `COPY` 源码，任何代码改动都会让整个 builder 重新执行。builder 只做拷贝和检查，耗时很短，可以接受。
- 发布阶段的 `COPY --from=builder` 按 `/export` 的内容判断。如果只改了测试文件，`/export` 内容不变，发布阶段直接命中缓存。

## 层数和 RUN 合并

每个 `RUN` 产生一层。相关命令合并到一个 `RUN` 里有两个好处：

- 层数少一些。
- 更重要的是，**在同一个 RUN 里创建又删除的文件不会留在任何层里**：

```dockerfile
# 好：apt 缓存在同一层被删除，不占镜像空间
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

# 差：第一层已经存下了 apt 缓存，第二层的 rm 无法回收
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
```

## 动手试一试

```bash
mkdir -p ~/docker-lab/ch08 && cd ~/docker-lab/ch08
echo 'v1' > code.txt
cat > Dockerfile <<'EOF'
FROM python:3.12-slim
RUN echo "slow step" && sleep 5
COPY code.txt /code.txt
EOF

docker build -t lab:ch08 .        # 第一次：sleep 5 秒
echo 'v2' > code.txt
docker build -t lab:ch08 .        # 第二次：RUN 显示 CACHED，只有 COPY 重新执行
```

把 `COPY` 移到 `RUN` 前面再试一次，改 `code.txt` 后 `sleep` 也会重跑。
