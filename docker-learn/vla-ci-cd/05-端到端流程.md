## 调用关系

```
bamboo.yaml
  └─ 调用 should_build.sh   （输出：构建什么、tag 是什么）
  └─ 调用 build.sh
        └─ docker build -f Dockerfile.env      （env 镜像）
        └─ docker build -f Dockerfile.release  （release 镜像，FROM env 镜像）
        └─ docker push                         ──► 镜像仓库

（这里断开，没有调用关系）

人工 docker compose up
  └─ 读取 docker-compose.yml
        └─ 从镜像仓库拉取 vla-*:${VLA_VERSION}
        └─ 启动容器
```

| 文件 | 谁调用它 | 它依赖什么 |
|---|---|---|
| `bamboo.yaml` | Bamboo，每次推送时 | `should_build.sh`、`build.sh` |
| `should_build.sh` | `bamboo.yaml` | 分支名、`ENV_VERSION`、提交信息 |
| `build.sh` | `bamboo.yaml`，也可以手动运行 | 两个 Dockerfile |
| `Dockerfile.env` / `Dockerfile.release` | `build.sh` | 仓库代码；release 还依赖 env 镜像 |
| `docker-compose.yml` | 人工 `docker compose up` | 镜像仓库里对应 tag 的镜像、宿主机数据目录 |

## 一次发版的完整过程

以发布 2.1.0 为例。

### 1. 在 release 分支上开发和测试

```bash
git checkout -b release/v2.1.0 dev
# 修改代码、提交、推送
git push origin release/v2.1.0
```

- 每次推送，CI 都构建并推送 `vla-body:2.1.0rc` 和 `vla-brain:2.1.0rc`，新的覆盖旧的。
- 依赖有变化时，同时把 `ENV_VERSION` 改成新版本号，比如 `1.2.0`，CI 会先构建 `vla-*-env:1.2.0`。

### 2. 在机器人上测试 rc 版本

```bash
cd body/gino/docker-compose
export VLA_VERSION=2.1.0rc
docker compose pull          # rc tag 会被覆盖，必须重新拉取
docker compose up -d
docker compose logs -f vla-brain
```

brain 会自动起推理服务，body 只运行 bash。确认机器人周围安全后，进入 body 容器手动启动（完整参数见 [04 章](04-docker-compose启动.md) "command：body 为什么只启动 bash" 一节）：

```bash
docker compose exec vla-body bash
python3 -m vla_body --mode runtime --joint-layout full-body ...
```

### 3. 合并到 master，产出正式版本

在 Bitbucket 上把 `release/v2.1.0` 合并到 master。合并提交的信息里含 `from release/v2.1.0`，CI 识别后构建 `vla-body:2.1.0` 和 `vla-brain:2.1.0`。

正式 tag 不会被覆盖，是一个固定不变的版本。

### 4. 部署正式版本

```bash
VLA_VERSION=2.1.0 docker compose up -d
```

## 常见问题

**推送后没有构建镜像？**
看第三阶段的日志里 `should_build.sh` 的输出。最常见的原因是分支名不符合 `release/vX.Y.Z`，比如写成了 `release/2.1.0` 或 `release/v2.1`。

**release 镜像构建失败，报找不到 env 镜像？**
`ENV_VERSION` 指向的 env 镜像在仓库里不存在。改了 `ENV_VERSION` 但 env 构建失败，或者在非 release 分支上改了它，都会出现这种情况。

**机器人上跑的不是最新代码？**
rc tag 被覆盖后，本地还是旧镜像，需要先 `docker compose pull`。可以用下面的命令确认镜像对应的提交：

```bash
docker inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' \
    robot-harbor.geekplus.com/gino/vla-brain:2.1.0rc
docker compose exec vla-brain sh -c 'echo $GIT_COMMIT'
```

**改了 docker-compose.yml，需要重新构建镜像吗？**
不需要。compose 文件不在镜像里，改完在机器人上重新 `docker compose up -d` 即可。

**更换模型权重，需要重新构建镜像吗？**
不需要。权重是挂载进去的。把新权重放到 `${VLA_DATA_ROOT}/checkpoints/` 下，改 compose 里的 `--config` 和 `--dir`，重启容器。

## 自测题

1. 在 `feature/xxx` 分支上推送，会构建镜像吗？会执行哪些阶段？
2. 在 `release/v2.1.0` 上改了 `Dockerfile.env` 但忘了改 `ENV_VERSION`，会发生什么？
3. 为什么 CI 里 env 镜像必须先于 release 镜像构建？
4. 机器人上忘了设置 `VLA_VERSION` 就执行 `docker compose up -d`，会发生什么？
5. 宿主机上没有 `/data/nvme/gino_motion_driver`，vla-body 能启动吗？
6. `docker compose up -d` 之后，机器人会自己动起来吗？为什么 vla-body 容器没有立刻退出？
7. brain 跑了一个月，容器日志会把磁盘写满吗？body 呢？

<details>
<summary>参考答案</summary>

1. 不会构建镜像。三个阶段都会执行，但第三阶段 `should_build.sh` 输出两个 `false`，脚本打印 "NO VLA IMAGE BUILD TRIGGERED." 后正常退出。第一阶段会严格检查 changelog 片段。
2. env 镜像不会重建，release 镜像仍基于旧的 env 镜像构建，`Dockerfile.env` 的改动不会生效。要么改 `ENV_VERSION`，要么在提交标题里加 `[build][vla-env]`。后者会用同一个版本号覆盖旧的 env 镜像。
3. release 镜像 `FROM vla-*-env:${ENV_TAG}`。同一次运行里如果 env 镜像也要更新，先构建 release 的话，它会基于旧的 env 镜像，或者新版本号的 env 镜像还不存在而直接失败。
4. compose 报错 `set VLA_VERSION, e.g. 2.1.0rc` 并退出，不会启动任何容器。这是 `${VLA_VERSION:?...}` 的作用。
5. 不能。这个挂载设置了 `create_host_path: false`，宿主机路径不存在时 compose 直接报错，不会创建空目录。
6. 不会。vla-body 的 `command` 是 `bash`，只开一个 shell，需要人 `exec` 进去手动启动 `python3 -m vla_body`。容器不退出是因为 `stdin_open: true` 让标准输入一直开着，bash 一直在等输入。
7. brain 不会，`logging` 限制了单文件 20 MB、最多 5 个，总共不超过 100 MB。body 没配 `logging`，容器日志不限大小，但它目前只运行 bash，输出很少。另外，两者挂载目录里程序自己写的日志不受这个限制。

</details>
