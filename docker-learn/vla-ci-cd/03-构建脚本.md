# 03 构建脚本：should_build.sh 和 build.sh

两个脚本都在 `embodied_algo/docker-deploy/vla/` 下，分工是：

| 脚本 | 回答的问题 |
|---|---|
| `should_build.sh` | 这次要不要构建？构建哪种镜像？tag 是什么？ |
| `build.sh` | 按给定的参数构建，并推送到镜像仓库 |

把"决定"和"执行"拆开，`build.sh` 就可以脱离 CI，在 Thor 上手动运行。

## 先回顾：两种镜像

| | env 镜像 | release 镜像 |
|---|---|---|
| 名字 | `vla-body-env` `vla-brain-env` | `vla-body` `vla-brain` |
| Dockerfile | `Dockerfile.env` | `Dockerfile.release` |
| 内容 | 第三方依赖 | env 镜像加业务代码 |
| tag 来源 | `ENV_VERSION` 文件，例如 `1.1.0` | release 分支名，例如 `2.1.0rc` 或 `2.1.0` |
| 重建频率 | 很少 | 每次发版 |

## should_build.sh：决定构建什么

用法：`should_build.sh <仓库目录> <分支名>`

输出固定四行，供 `bamboo.yaml` 解析：

```
VLA_ENV_SHOULD_BUILD=true|false
VLA_ENV_TAG=1.1.0
VLA_RELEASE_SHOULD_BUILD=true|false
VLA_RELEASE_TAG=2.1.0rc
```

### 判断规则

| 分支 | release 镜像 | env 镜像 |
|---|---|---|
| `release/v2.1.0` | 每个提交都构建，tag 是 `2.1.0rc` | `ENV_VERSION` 在本次提交里改了，或提交标题含 `[build][vla-env]`，才构建 |
| `master` | 只有合并 release 分支的那个提交才构建，tag 是 `2.1.0` | 从不构建 |
| 其他分支 | 不构建 | 不构建 |

几点说明：

- **rc tag 会被覆盖**：同一个 release 分支上每次提交都推送 `2.1.0rc`，新的覆盖旧的。机器人上想拿到最新的 rc，需要重新 `docker compose pull`。
- **怎么识别合并提交**：Bitbucket 合并 PR 时，提交信息里会写 `Merge pull request ... from release/v2.1.0 ...`。脚本用正则匹配 `from release/vX.Y.Z`，取出版本号。直接在 master 上提交，不会构建镜像。
- **怎么判断 ENV_VERSION 改了**：比较 `HEAD` 和 `HEAD^`（上一个提交）里 `ENV_VERSION` 文件的内容。
- **master 不构建 env 镜像**：它直接复用在 release 分支上构建好的 env 镜像。
- **ENV_VERSION 格式检查**：不是 `X.Y.Z` 格式时，脚本报错退出。

### 什么时候需要改 ENV_VERSION

改了 `Dockerfile.env`、`pyproject.toml` 或 `constraints.txt`，也就是第三方依赖变了，就把 `ENV_VERSION` 的版本号加一，在 release 分支上提交。CI 会构建新的 env 镜像，并让同一次运行里的 release 镜像基于它构建。

只想用同一个版本号重建 env 镜像（比如上次推送失败），就在提交标题里加 `[build][vla-env]`。

## build.sh：构建和推送

用法：

```bash
build.sh env     --tag <env-tag>                     [--push] [--target body|brain]
build.sh release --tag <tag> [--env-tag <env-tag>]   [--push] [--target body|brain]
```

| 参数 | 含义 |
|---|---|
| `env` / `release` | 构建哪种镜像 |
| `--tag` | 产出镜像的 tag，必填 |
| `--env-tag` | release 镜像基于哪个 env 镜像，默认读 `ENV_VERSION` |
| `--push` | 构建完推送到镜像仓库 |
| `--target` | 只构建 body 或 brain，默认两个都构建 |

### 它做了什么

1. 检查参数，检查当前机器是 aarch64，不是就报错退出。
2. 读取当前的 git 提交号。
3. 对 body 和 brain 各执行一次 `docker build`：

| | env | release |
|---|---|---|
| `--file` | `Dockerfile.env` | `Dockerfile.release` |
| `--target` | `vla-body` 或 `vla-brain` | `vla-body` 或 `vla-brain` |
| `--build-arg` | 无 | `ENV_TAG`、`GIT_COMMIT`、`RELEASE_VERSION` |
| 构建上下文 | `docker-deploy/vla/` 目录 | 仓库根目录 |
| 产出 | `robot-harbor.geekplus.com/gino/vla-body-env:<tag>` | `robot-harbor.geekplus.com/gino/vla-body:<tag>` |

4. 有 `--push` 时，用 `GEEK_DOCKER_USER` 和 `GEEK_DOCKER_KEY` 登录镜像仓库，再逐个 `docker push`。密码通过 `--password-stdin` 传入，不会出现在命令行和进程列表里。

### 构建上下文为什么不同

- env 镜像只需要 `pyproject.toml` 和 `constraints.txt`，它们都在 `docker-deploy/vla/` 下，上下文用这个目录就够了。
- release 镜像要拷贝 `brain/vla/openpi` 和 `body/gino`，上下文必须是仓库根目录，再用 `Dockerfile.release.dockerignore` 过滤。

### 手动构建

在 Thor 上，仓库根目录执行：

```bash
# 只构建不推送，本地测试用
docker-deploy/vla/build.sh release --tag test --target brain

# 构建并推送
export GEEK_DOCKER_USER=... GEEK_DOCKER_KEY=...
docker-deploy/vla/build.sh release --tag 2.1.0rc --push
```

注意：release 镜像依赖的 env 镜像，本地或镜像仓库里必须已经存在，否则 `FROM` 会失败。
